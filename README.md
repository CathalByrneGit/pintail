# Pintail

> **A terminal admin console for [Quack](https://duckdb.org) and
> [DuckLake](https://ducklake.select) servers.** Not a SQL IDE — for
> ad-hoc exploration use [Harlequin](https://harlequin.sh) or
> [DuckDB's local UI](https://duckdb.org/2025/03/12/duckdb-ui).

Pintail is for the operational side of running DuckDB-as-a-server:
connection topology, token administration, TLS reverse-proxy generation,
DuckLake snapshot inspection, per-token auth policy editing, and a small
SQL scratchpad for quick admin checks. It targets teams running Quack
in production with multi-writer DuckLake setups — not data analysts.

Built with [Bubble Tea](https://github.com/charmbracelet/bubbletea),
[Bubbles](https://github.com/charmbracelet/bubbles), and
[Lip Gloss](https://github.com/charmbracelet/lipgloss). Single static
binary; shells out to the `duckdb` CLI for live operations.


## What this is — and isn't

| You want to…                                          | Use this              |
|-------------------------------------------------------|-----------------------|
| Explore data, write multi-statement queries, autocomplete, themes, plugins | **[Harlequin](https://harlequin.sh)** — Python+Textual SQL IDE |
| Build SQL notebooks against local DuckDB             | **[DuckDB Local UI](https://duckdb.org/2025/03/12/duckdb-ui)** — browser-based, official |
| Browse a DuckDB file in the browser                  | **[Duck UI](https://github.com/iberodatabr/duck-ui)** — WASM-based |
| Operate a Quack/DuckLake server: tokens, TLS, snapshots, multi-server ping, auth policies | **Pintail** (this) |

The scratchpad here is intentionally minimal — a place to run quick
verification queries (does the token work? what's the row count after
rollback? are sessions live?) without leaving the admin tool. For real
exploration work, reach for Harlequin or DuckDB's local UI.

## Three connection types

Each configured connection has a `type` and the client adapts its ping,
query routing, and metadata fetch accordingly.

| Type       | Use it for                          | Reachability                     | Query routing                                                                                                          |
|------------|-------------------------------------|----------------------------------|------------------------------------------------------------------------------------------------------------------------|
| `quack`    | Remote DuckDB via Quack             | TCP `host:port`                  | `ATTACH 'quack://…' AS _remote (TOKEN '…'); USE _remote;`                                                              |
| `local`    | Plain `.duckdb` file on disk        | `os.Stat(path)`                  | `duckdb <path> -json -c "<sql>"` (file opened directly via argv)                                                       |
| `ducklake` | DuckLake lakehouse                  | TCP dial of catalog host / stat  | `INSTALL ducklake; LOAD ducklake; ATTACH 'ducklake:…' AS _lake (DATA_PATH '…'); USE _lake;`                            |

### DuckLake catalog via another connection (multi-writer pattern)

A DuckLake config can reference another configured connection as its
catalog instead of using a freeform URL. This is the deployment pattern
Quack was designed for: one central DuckDB exposed via Quack, multiple
writers reaching the lake through it.

```json
{ "name": "central-catalog", "type": "quack", "host": "catalog.internal", "port": 9494, "token": "qk_…" },
{ "name": "lake-prod",       "type": "ducklake", "catalog_ref": "central-catalog", "storage_path": "s3://datalake-prod/lake" }
```

Pintail emits the two-step attach automatically:

```sql
INSTALL ducklake; LOAD ducklake;
ATTACH 'quack://catalog.internal:9494' AS _catalog (TOKEN 'qk_…');
ATTACH 'ducklake:_catalog' AS _lake (DATA_PATH 's3://datalake-prod/lake');
USE _lake;
```

`catalog_ref` also works pointing at a `local` connection (a local
DuckDB file as catalog) or any other configured connection. Use
`catalog_path` instead when you want a literal freeform URL — DuckLake
supports `postgres://…`, `mysql://…`, `sqlite:///path/to/catalog.sqlite`,
or a bare path to a `.duckdb` or `.sqlite` file (extension-based detection).

## Features

| Screen                  | Key | What it does                                                                                                            |
|-------------------------|-----|-------------------------------------------------------------------------------------------------------------------------|
| **Dashboard**           | —   | Live ping status for every connection, sessions table, catalog tree                                                     |
| **Secrets**             | `t` | Two modes (toggle with `tab`): **Quack tokens** for server auth, **Storage secrets** for object-store credentials       |
| **SQL scratchpad**      | `s` | Quick verification queries; **CSV / Parquet export** via `ctrl+e` (for audit trails, not analytics)                     |
| **DuckLake snapshots**  | `l` | List `<catalog>.snapshots()`; renders time-travel and `ducklake_expire_snapshots` SQL                                   |
| **TLS config**          | `x` | Generate Caddy / Nginx / Envoy reverse-proxy configs for HTTPS termination                                              |
| **Auth policy**         | `p` | Toggle per-token SQL permissions; emit `ALTER SECRET` statements                                                        |
| **Connections**         | `a` | Add, edit, delete connections; persisted to `~/.duckdb/pintail.json`                                                   |

### Storage secrets

The secrets screen (`t`) has two modes — `tab` toggles between them:

- **Quack tokens** — bearer tokens for `quack` connections
- **Storage secrets** — credentials for object stores (S3 / R2 / GCS / Azure)

Storage secrets are needed whenever DuckDB has to reach over the network to read data — almost always for `ducklake` connections (the `storage_path` is usually remote), and optionally for `local` connections when the database file path is itself a URI (`s3://bucket/db.duckdb`) or queries reach remote Parquet. `quack` connections don't use them; the Quack server has its own credentials.

A connection references a storage secret by name:

```json
{
  "name": "lake-prod",
  "type": "ducklake",
  "catalog_ref": "central-catalog",
  "storage_path": "s3://datalake-prod/lake",
  "storage_secret_ref": "lake_s3"
}
```

Pintail injects the `CREATE SECRET` ahead of the ATTACH automatically:

```sql
INSTALL httpfs; LOAD httpfs;
CREATE OR REPLACE SECRET _storage (TYPE s3, KEY_ID '…', SECRET '…', REGION 'us-east-1', SCOPE 's3://datalake-prod/lake');
INSTALL ducklake; LOAD ducklake;
ATTACH 'quack://catalog.internal:9494' AS _catalog (TOKEN 'qk_…');
ATTACH 'ducklake:_catalog' AS _lake (DATA_PATH 's3://datalake-prod/lake');
USE _lake;
-- your query
```

Secrets are stored in plaintext under `storage_secrets` in `~/.duckdb/pintail.json` — file permissions are your responsibility. For real key management, paste values from Vault / 1Password / your secret store; Pintail doesn't try to be one.

### DuckLake snapshots

The `l` screen lists the most recent 50 rows from `<catalog>.snapshots()`
for the targeted DuckLake connection. The detail panel shows every column
returned, plus two ready-to-paste SQL blocks:

- **Time-travel read** — `SELECT … FROM <table> AT (VERSION => N)` — non-destructive.
- **Expire snapshot** — `CALL ducklake_expire_snapshots('_lake', versions => [N])` — destructive, removes data files permanently.

Neither is run from this screen by design; you copy the SQL into the
scratchpad (or your tool of choice) to actually execute.

### Scratchpad export

After running a query, `ctrl+e` opens an export prompt: `c` writes CSV
from in-memory rows (no external tools), `p` re-executes through
`duckdb -c "COPY (…) TO '…' (FORMAT PARQUET);"`. Files land in
`~/.duckdb/exports/pintail-{YYYYMMDD-HHMMSS}.{csv|parquet}`. Designed
for audit trails — capture the result of a permission change or a
post-rollback row count, not for analytical workflows.

### Connection manager

`a` opens the connection manager. The left panel lists every configured
connection with live status; the right panel is the add/edit form. On
the list: `e` edits the selected entry, `d` deletes it (last-remaining
deletion is blocked to prevent lockout), `→` returns to the form. Any
save/delete rebuilds all in-memory clients so DuckLake `catalog_ref`
lookups always see the latest state.

## CLI subcommands

Inspired by [msgvault](https://github.com/kenn-io/msgvault), Pintail
also has a small CLI surface for scripting. All commands use the same
`~/.duckdb/pintail.json`.

```bash
pintail                            # launch the TUI (default)
pintail list                       # human-readable list
pintail list --json                # for scripts
pintail ping prod-quack            # one-shot reachability check
pintail ping lake-prod --json      # exit code + JSON
pintail query lake-prod "SELECT * FROM orders LIMIT 5"
pintail query lake-prod "SELECT COUNT(*) FROM orders" --json
pintail help
```

`query` requires `duckdb` on `$PATH` and uses the same type-aware
routing as the scratchpad — including `catalog_ref` resolution.

## Polling cadence

Three independent timers keep subprocess spawning under control:

- **Ping** (5s) — cheap reachability check (TCP dial or file stat). No subprocess.
- **Sessions** (15s) — refreshes sessions/snapshots for *online* connections.
- **Catalog** — fetched once on each offline→online transition, plus on demand via `r`.

## Architecture notes

- **Elm architecture** — each screen is a sub-model with its own
  `Update`/`View`; the root `Model` routes messages and composes layouts.
- **All I/O async** — pings, queries, snapshot fetches, and metadata
  polls run as `tea.Cmd` goroutines and deliver typed messages back to
  the update loop. The UI never blocks.
- **Catalog-ref resolution via injected closure** — each `QuackClient`
  holds a `ConfigResolver` (closure over `[]ServerConfig`). DuckLake's
  `AttachPrefix` uses it to look up `CatalogRef` at query time.
- **Clients rebuilt on any config mutation** — add/edit/delete all call
  `InitClients(m.configs)` so the shared resolver reflects the latest state.
- **One subprocess strategy** — rather than implementing DuckDB's binary
  wire protocol in Go (which would require CGo), Pintail shells out to
  the `duckdb` CLI with `-json` and parses results. This makes Quack /
  Local / DuckLake all work uniformly.
